## Architecture

DeFi liquidity position tracker. Next.js 16 App Router with wagmi v3 for wallet connection and on-chain data fetching.

### Data Flow

When a wallet is connected, the dashboard fetches LP positions from three API routes in parallel (`/api/aerodrome`, `/api/uniswap/v3`, `/api/velodrome`). Each route makes raw RPC calls to on-chain contracts via Alchemy, decodes ABI-encoded hex responses manually (no ethers/viem contract abstractions), then enriches with CoinGecko prices and DefiLlama APY data. Without a wallet, 8 hardcoded demo positions from `app/data/positions.ts` are shown.

### API Routes (server-side on-chain fetching)

- `app/api/aerodrome/route.ts` — Reads Aerodrome CL positions on Base via Sugar contract. Decodes packed uint256 fields (15 per position) from raw hex.
- `app/api/uniswap/v3/route.ts` — Reads Uniswap V3 NFT positions on Ethereum/Arbitrum/Polygon/Optimism via NonfungiblePositionManager. Estimates token amounts using sqrt-price tick math.
- `app/api/velodrome/route.ts` — Reads Velodrome CL positions on Optimism via Sugar contract. Same decode pattern as Aerodrome.

All three routes share a common output shape (`AerodromePosition` interface in `app/lib/aerodrome.ts`) with fields: id, pair, protocol, chain, value, apy, fees, status.

### Client Libraries

`app/lib/{aerodrome,uniswap,velodrome}.ts` — Thin fetch wrappers calling the corresponding API routes. All return `AerodromePosition[]` (the shared position type).

### Key Patterns

- **Manual ABI decoding**: API routes decode raw `eth_call` hex responses by slicing 64-char words rather than using library-level contract calls. Token addresses resolved via hardcoded `TOKENS`/`KNOWN_TOKENS` lookup maps per chain.
- **Price enrichment**: CoinGecko for token prices (60s revalidation), DefiLlama yields API for APY data (300s revalidation). Median APY used for token-pair fallback matching.
- **Wallet**: Single injected connector (MetaMask). Config in `app/config/wagmi.ts` supports mainnet, Base, Arbitrum, Optimism, Polygon, Avalanche.
- **Provider wrapping**: `app/providers.tsx` wraps app with WagmiProvider + React Query. All pages using hooks must be `"use client"`.
- **Auto-refresh**: `PositionsContext` uses `refetchInterval: 60_000` + `placeholderData: keepPreviousData` for smooth background refresh with no layout shift. Exposes `isFetching`, `dataUpdatedAt`, `refetch`. Dashboard shows "Updated X ago" + manual refresh button (spinning icon while fetching).
- **Portfolio history**: `app/hooks/usePortfolioHistory.ts` — saves `{timestamp, totalValue, positionCount}` snapshots to localStorage (`lp-portfolio-history`) on every positions refresh (every 60s). Caps at 1000 points (oldest pruned); keeps 30 days by age. Chart shows after ≥2 points (appears within ~1 minute on first load). Range buttons (1D/7D/30D/90D/1Y) filter snapshots; if range has <2 points, falls back to all available data and labels P&L "since [date]". No 24h gate.

## Portfolio snapshots (daily Neon + client-push hybrid)

`vercel.json` registers a single cron: `/api/cron/daily-snapshot` at `0 0 * * *` (midnight UTC). The system is protocol-agnostic and works for any wallet on any chain that flows through the dashboard.

- **Tables** (schema lives in `scripts/setup-db.sql`): `wallets` (id, wallet_address, created_at) and `portfolio_snapshots` (wallet_address, total_value, lp_value, lending_value, token_value, position_count, timestamp). "One snapshot per (wallet, UTC day)" is enforced at the save layer — the save route deletes any prior row for today's UTC date before inserting.
- **Client push** (`app/hooks/useSnapshotPortfolio.ts`): on every positions refresh, the dashboard POSTs the current per-wallet totals to `/api/snapshots/save`. A `lastSavedRef` signature (`addrs|value*100`) dedupes identical values so we don't spam the endpoint. When multiple wallets are connected/watched, the full totals are attributed to the first address and zeros to the rest — the range endpoint sums across wallets, so aggregated history remains correct.
- **Range read** (`app/api/snapshots/range/route.ts`): `GET ?address=addr1,addr2,…&days=365` returns snapshots summed per timestamp bucket for multi-wallet aggregation, plus `trackingSince` (earliest row anywhere for those addresses) and `daysTracked`. The client fetches once at 1Y and derives 1D / 7D / 30D in memory.
- **Cron** (`app/api/cron/daily-snapshot/route.ts`): for every wallet with at least one prior snapshot, carries forward the most recent value into a fresh row stamped at `NOW()` unless a row already exists for that wallet today (UTC). The cron never refetches on-chain state server-side — that would require reimplementing every protocol pipeline in a serverless function. Its job is purely continuity for days when the user doesn't open the app.
- **Hero toggle UI** (`app/dashboard/page.tsx`): `useSnapshotPortfolio` returns `byRange[key]` with `{value, oldestValue, oldestTimestamp, pnlDollar, pnlPct, available, checkBackInDays}` for each key in `"1D" | "7D" | "30D" | "1Y"`. **Strict gating** — a range is `available: true` only when there are ≥2 snapshots in the range AND the oldest / newest snapshots are at least `MIN_HOURS_APART[key]` apart (1D = 20h, 7D = 6d, 30D = 25d, 1Y = 300d). A single snapshot NEVER produces a non-zero percentage. When `available` is false, the hook exposes `checkBackInDays` = max(0, ceil(minDaysNeeded − daysSinceTrackingStart)) and the dashboard shows `"Not enough data yet — check back tomorrow"` for 1D or `"Tracking started {date} — check back in {N} days"` for 7D / 30D / 1Y. The localStorage-based `usePortfolioHistory` hook is still wired for the Portfolio Performance *chart* only; all P&L numbers on the hero now come from Postgres.
- **Address normalization**: EVM and Sui addresses are lowercased before building the snapshot `addrKey`; Solana base58 is kept case-sensitive. The dashboard builds `snapshotAddresses` from connected + watched wallets (deduped) so the snapshot stream aligns with the PositionsContext fetch set.

## LP P&L (on-chain, aggregated)

The analytics page computes portfolio-wide LP P&L entirely on-chain — there is **no snapshot cron, no database read, no "Take Snapshot" button, no historical chart, no localStorage cache**. The DB-backed snapshot system was removed; the `wallets` / `portfolio_snapshots` / `position_snapshots` tables and `scripts/setup-db.sql` are intentionally left in place in the repo but no code reads from or writes to them anymore. The orphaned `useDbPortfolioHistory` / `useDbPositionHistory` hooks are stubbed no-ops so the legacy `/dashboard/[id]` route still compiles.

- **Per-position P&L**: `app/lib/positionPnl.ts` `computePositionPnL` — strict pure function. Hard-fails with `{ok:false}` for three reasons: `no_deposits` (zero deposit events), `missing_deposit_prices` (any deposit lacks both `usdAtTime` and historical per-token prices), `missing_current_prices` (current price0/price1 not available). There is NO fallback to current prices for initial value — every deposit must carry real historical pricing or the position is excluded. **IL formula (concentrated-liquidity, exact)**: HODL Value = Σ(deposited_amount_token × current_price_token); IL USD = LP Value − HODL Value (negative when LP underperforms HODL); IL % = (LP Value / HODL Value − 1) × 100. The identity `hodlValue + ilUSD === liveValue` holds **exactly** — there is no √r approximation, no V2-pool assumption, and no unexplained discrepancy between HODL Value and Current Value. `liveValue` = `currentValue` for open positions and `closingValue` for closed positions. This formula is protocol-agnostic: it only requires deposit amounts (already emitted by every activity route as `amount0`/`amount1`) plus current per-token prices (already passed in by callers) — so any new chain or protocol added in the future automatically gets a correct IL calculation with zero IL-specific code. For **open** positions Net P&L = (Current + Fees Collected + Fees Unclaimed) − Initial. For **closed** positions (`isClosed: true`): Closing Value = sum of withdrawal event USD values (from on-chain V3 price derivation at withdrawal time); Net P&L = (Closing Value + Fees Collected) − Initial Value. The position detail page shows "Closing Value" instead of "Current Value" for closed positions and hides "Fees Unclaimed". The `PositionPnLData` interface exposes `closingValue`, `isClosed`, `totalAmount0`, `totalAmount1` (raw deposited amounts, used to render the HODL formula in the "How this was calculated" collapsible).
- **Aggregated LP P&L hook** (`app/hooks/useLpPnl.ts` `useLpPnl`): standalone hook that takes the positions array, fetches activity for each deduplicated position, calls `computePositionPnL`, and returns aggregated totals (`initialValue, currentValue, feesCollected, feesUnclaimed, ilUSD, netPnl, netPnlPct, included, excluded, isLoading`) PLUS `perPosition: Record<string, PositionPnLData>`, `excludedPositions: ExcludedPosition[]`, and `estimatedPositionCount: number`. **excludedPositions** lists every position that's NOT contributing to the totals (unsupported protocols like Cetus/Momentum, missing-data positions, transport errors after 3 retries) with a user-friendly `reason` string already mapped — the analytics page renders these in an amber warning row below the 6 stat cards. **estimatedPositionCount** counts positions that ARE included via the HyperEVM fallback (see next bullet); the analytics "Total Deposited" card prefixes its value with `~` when this is > 0. **HyperEVM fallback rationale**: `rpc.hyperliquid.xyz/evm` doesn't expose archival eth_getLogs to retrieve historical deposit events, so HyperEVM positions (HyperSwap / KittenSwap / ProjectX) would otherwise be silently excluded with `reason: "no events"`. Instead, when the activity scan returns 0 events for a HyperEVM position with `pos.value > 0`, `fetchAndCompute` returns `{ok: true, data: buildFallbackPnL(pos), fallback: true}` where the synthetic `PositionPnLData` uses the current value as the deposit estimate (`initialValue = currentValue`, `feesCollected = 0`, `feesUnclaimed = pos.fees`, `netPnlUSD = unclaimed`, `ilUSD = 0`, `ilAvailable = false`). The position is INCLUDED in the totals so TOTAL DEPOSITED and CURRENT VALUE both reflect it; the `~` marker on the aggregate card explains the estimate. **Reason mapping** lives in `userFriendlyReason(reason, protocol)` — adds chain-specific context (e.g. `"Deposit history unavailable on HyperEVM RPC"` instead of the raw `"no events"` reason). PER-POSITION metadata (pair / protocol / chain) needed for the warning is collected during the eligibility filter step into a `positionMetaRef` map and passed into `aggregate()` alongside the `unsupportedRejectionsRef` list (positions rejected because their protocol isn't in `ACTIVITY_PROTOCOLS` — Cetus, Momentum, etc.). NEVER call `computePositionPnL` directly in a row component — always read from `useLpPnl.perPosition` so a single change to the math touches every surface at once. **Closed positions are excluded** from totals — analytics shows the *current* state of the portfolio, not historical performance. Eligibility filter rejects `status === "Closed"` OR `value <= 0` before any aggregation. **Per-position localStorage cache** with 5-minute TTL on the on-chain events fetch (key `lp-pnl-events-v1-{posId}`): on first visit the slow on-chain history is fetched and stored; subsequent visits within 5 min serve events instantly from cache and recompute P&L locally with the latest live prices/value (so prices stay fresh while history loads instantly). Empty-result fetches are also cached (with `events: null` + reason) to avoid hammering routes that have no on-chain history (the HyperEVM fallback re-applies on cache-hit, so cached emptiness still produces a fallback PnL on the next render). The cache is intentionally for events only — `computePositionPnL` always runs against current `pos.value` / `pos.price0` / `pos.price1` / `pos.fees`. Each position logs exactly once to the console from inside `fetchAndCompute`. Positions are deduplicated by `pos.id` (Aerodrome ids are `aero-{sugarPositionId}` which is the on-chain Sugar position id — unique per NFT, no collision possible between two distinct WETH/USDC positions). The dashboard positions table reads `lpPnl.perPosition[pos.id].netPnlUSD` / `.netPnlPct` for each row's P&L cell; this guarantees that summing every visible row's pnlUsd across the dashboard equals `lpPnl.netPnl` exactly (for non-closed positions). - **Activity routes use V3 price derivation — NO CoinGecko historical prices**: all 8 activity routes (Aerodrome, Bluefin, Orca, Raydium, HyperSwap, Uniswap V3, Velodrome, PancakeSwap) derive USD prices from on-chain V3 math (`app/lib/v3PriceDerivation.ts`) for both **deposit AND withdrawal** events — no CoinGecko `/coins/{id}/history` calls. The shared `deriveDepositPrices()` back-solves for pool sqrtPrice from token amounts + tick range using the quadratic formula, then anchors to USD via stablecoin detection (if one token in the pair is a known stablecoin, its price is $1 and the other token's price is derived from the pool ratio). This works for all close scenarios: upside (all quote token), downside (all base token), and in-range (both tokens). Each route has a `STABLECOINS` set for its chain. The `useLpPnl` hook passes `tickLower`/`tickUpper` as query params to all activity APIs.
- **Fee-claim USD uses historical sqrtPrice at the claim block (EVM V3 routes)**: all 5 EVM activity routes (Aerodrome, Uniswap V3, Velodrome, HyperSwap, PancakeSwap) accept a `pool` query param and, when it's supplied, resolve the pool's `sqrtPriceX96` via `eth_call(slot0(), blockNumber)` at each unique fee-claim block through the shared helper `app/lib/v3HistoricalFeePrice.ts` (`createHistoricalFeePriceResolver`). The sqrt-price is converted to `human_price_of_token0_in_token1 = (sqrtPriceX96/2^96)^2 * 10^(d0-d1)`, then stablecoin-anchored (stable token → $1, other side derived from the ratio). `usdAtTime = amount0 * price0_at_block + amount1 * price1_at_block` per claim — both tokens valued at their EXACT block-of-claim prices, not current prices and not averages. The resolver caches by `(pool, blockHex)` for the request lifetime and runs up to 6 `eth_call`s concurrently. Fails gracefully when the pool has no stablecoin in the pair (returns null → caller falls back to current-price × amounts). `useAllPositionsActivity.buildActivityUrl` now always forwards `pool={pos.poolAddress}` when the position carries it (Aerodrome / Velodrome / HyperSwap routes populate it from on-chain lookups; Uniswap V3 / PancakeSwap would need a `factory.getPool(token0,token1,fee)` call in their position routes to enable this path). Solana (Orca / Raydium) and Sui (Bluefin) cannot use this technique without an archival RPC, so they keep their existing current-price fallback for fee claims.
- **`useAllPositionsActivity`**: still exists and returns `{perfMap, eventsMap, isLoading}` for the analytics Position Performance table, rankings, and the Fee Income chart. `eventsMap` is consumed by the analytics Fee Income section (SECTION 2) to build per-protocol and time-bucketed fee aggregates. It is NOT consumed by LP P&L (which uses `useLpPnl` instead).
- **SITE-WIDE RULE: feesCollected always uses CLAIM-TIME USD price, NEVER current price. feesUnclaimed uses current price.** Every activity route in `app/api/*/activity/` MUST populate `usdAtTime` on every `fee_claim` / `reward_claim` event using the price at the claim's block (EVM V3 routes do this via `createHistoricalFeePriceResolver` reading `slot0()` at the claim block; Solana/Sui derive from on-chain V3 math; new chains MUST follow the same rule). The secondary fallback is `amount0 * price0AtTime + amount1 * price1AtTime` (still historical). Defaulting to 0 is acceptable; defaulting to **current price is NOT** — that would inflate fees collected for users whose claimed tokens have since appreciated and deflate for users whose claimed tokens have since depreciated, which is unfair and wrong. Conversely `feesUnclaimed` is computed from `pos.fees` which IS today's mark — that's correct because unclaimed fees are economically valued at what you'd get if you claimed RIGHT NOW.
- **Analytics LP P&L "Fees Collected" card reads `feeIncome.totalAllTime` (lifetime), NOT `useLpPnl.feesCollected`**: `useLpPnl.feesCollected` only reflects fees from positions still open today (the eligibility filter excludes closed positions). For any wallet whose positions have churned, that undercounts the true lifetime claimed total — which is exactly why the LP P&L "Fees Collected" card displayed $720 while the Fee Income chart above showed $3,409 against the same wallet. Fix: the analytics page LP P&L card array (`app/analytics/page.tsx` around line 1295) shadows `lpPnl.feesCollected` with `feeIncome.totalAllTime` for the Fees Collected display, and recomputes the Net P&L card's value as `lpPnl.currentValue + feeIncome.totalAllTime + lpPnl.feesUnclaimed - lpPnl.initialValue` so the two numbers stay consistent. `feeIncome.totalAllTime` is built by SECTION 2's `feeIncome` memo, which walks `useAllPositionsActivity.eventsMap` (fetches activity for ALL positions including closed) PLUS `useWalletLevelFees().events` (Bluefin `positionId=all` mode, recovers fees from fully-destroyed Sui objects), filters to `type === "fee_claim" || "reward_claim"`, prefers `usdAtTime`, falls back to `amount0 * price0AtTime + amount1 * price1AtTime`, and dedupes overlap by `(protocol, txHash, amount0, amount1)`. IL, Initial Value, Current Value still come from `useLpPnl` (open positions only) by design — only the Fees Collected and Net P&L cards consume the lifetime number. Adding a new chain or protocol automatically lights up here as long as its activity route emits `type: "fee_claim"` events with claim-time `usdAtTime` (or claim-time per-token prices) and a `txHash`.
- **Analytics page `hasWallet` check mirrors dashboard**: the analytics page (`app/analytics/page.tsx`) reads `watchedWallets` from `WatchedWalletsContext` and computes `hasWallet = mounted && (!!(address || solanaAddress || suiAddress) || watchedWallets.length > 0)` — identical to the dashboard. Positions already flow through `PositionsContext` which fetches for both connected wallets AND saved Manage Wallets entries, so once the gate is correct the full analytics view renders automatically for users who only have saved addresses.
- **Analytics SECTION 2 — Fee Income chart (replaces the old Portfolio Value chart)**: `app/analytics/page.tsx` shows a cumulative fee-income line chart with 1D/7D/30D/90D/180D/1Y pills (default 30D) plus a horizontally scrollable protocol breakdown row below it. Data source: `useAllPositionsActivity.eventsMap` merged with `useWalletLevelFees().events` — for every position, iterate events, keep only `type === "fee_claim" || type === "reward_claim"` with finite `usdAtTime > 0`, attach that position's `protocol` + `chain`, flatten and sort by timestamp. The headline big number is `feeIncome.totalWindow` (fees claimed in the selected range) — it updates every time the user switches the pill. A muted `"Lifetime: ${totalAllTime}"` caption sits under the headline so the all-time total is still visible. The chart's `series` starts at 0 at `rangeCutoff`, adds each in-window claim to a running total, and anchors a final point at `Date.now()`. Protocol breakdown cards: group in-window fees by `${protocol}::${chain}`, drop zeros, sort desc by USD, compute `pct = usd / totalWindow * 100`, render as fixed-width (190px) cards inside `overflow-x-auto` with a colored left border pulled from `PROTOCOL_COLORS`. Headline + chart + protocol cards all react to the same `rangeKey` so they stay consistent. Protocols appear automatically from `positions[].protocol`/`.chain` — new protocols added to any position API route show up with no analytics-page change. `usePortfolioHistory` is still called here (keeps localStorage snapshots alive for the dashboard's Portfolio History chart) but its derived `chartData`/`pnlDollar`/`pnlPct`/`pnlLabel`/`effectiveHistory` are now unused on this page.
- **`useLpPnl` retry policy + per-attempt timeouts**: every per-position activity fetch in `app/hooks/useLpPnl.ts` runs through `fetchEventsAttempt(url, tag, timeoutMs)` wrapped by a retry loop in `fetchAndCompute`. **3 attempts total** (1 initial + 2 retries per user spec) with per-attempt timeouts `[30s, 30s, 45s]` and backoff `[0, 1s, 2s]` between attempts — the final attempt gets the most patience to handle slow archival RPCs (Tenderly chain). Retries fire ONLY for transport errors (`timeout` / `fetch error` / `HTTP …`); definitive failures (HTTP 4xx route errors, empty-events responses) skip retries since retrying won't change the answer. Empty-events results are cached with `events: null` so the second visit doesn't re-hit the route. After all 3 attempts fail, the position is classified as an `errored` transport failure and surfaces in the red banner. `LpPnlResult` exposes `errored: number` + `errorReasons: string[]` alongside `included`/`excluded`/`isLoading`. Transport errors are detected via `ERROR_REASONS = { "timeout", "fetch error", "no activity URL" }` + anything starting with `"HTTP "`; legitimate empty-history reasons (`no_deposits`, `missing_deposit_prices`, etc.) still count as `excluded`. The analytics LP P&L section renders: a small emerald spinner next to the heading while `isLoading`; **shimmer-bar skeletons in EVERY one of the 6 stat-card values for the entire `isLoading === true` window** — partial totals NEVER reveal as positions arrive (the "loading N of M" intermediate state was deliberately removed; the user sees no numbers until ALL positions across all chains have completed); subtitles change to `"calculating…"` while loading and revert to their static descriptions afterwards; a red banner listing the error reasons when `errored > 0` ("Couldn't load N position(s) — timeout, HTTP 500 — The RPC didn't respond in 30s. Totals below are for the positions that did load."). Failed positions count as `errored` in the banner but do NOT block the spinner from clearing — `isLoading = inflight > 0`, so once every fetch has either resolved or errored, the totals reveal at once. The shimmer keyframes (`@keyframes lp-pnl-shimmer`) are inlined right below the grid.
- **`computePositionPnL` deposit acceptance is permissive (avoids silent exclusions)**: `app/lib/positionPnl.ts` filters out truly empty deposit events (`amount0 === 0 && amount1 === 0`) up front — some Sui Move emitters fire a zero-amount `LiquidityProvided` on the first add or on protocol-side rebalances, and those rows would otherwise fail the per-deposit price check and exclude the whole position. The deposit price check itself now accepts ANY of: (a) historical per-token prices set, (b) `usdAtTime > 0` set by the route, (c) at least one priced side (a non-zero amount with a non-zero per-token price) — covering non-stable pairs where `deriveDepositPrices` returns null and only one fallback is populated. Each deposit's contribution to `initialValue` uses `usdAtTime` when present, otherwise falls back to `amount0 * (price0AtTime ?? 0) + amount1 * (price1AtTime ?? 0)`. Net effect: the analytics LP P&L section never silently excludes a position that has a real on-chain deposit just because one side's price is missing.

## Security Rules

CRITICAL: Wallets must ONLY show as connected when the user has actively unlocked and connected them. A locked wallet must NEVER auto-connect to the site. This applies to ALL chains — EVM, Solana, Sui, and any future chains. Always use explicit user consent tracking (not just checking if a public key exists) to determine connection state.

**Implementation**: `WalletAuthContext` (`app/contexts/WalletAuthContext.tsx`) stores `solanaAddress: string | null` — the actual address, set only after a user-initiated connect succeeds. Use the adapter (e.g. `useWallet()`) ONLY for mechanics: listing wallets, calling select/connect/disconnect. Never read `connected` or `publicKey` from the adapter for display — a locked Phantom wallet keeps those truthy via Wallet Standard silent reconnect. All components (Navbar, PositionsContext, Dashboard, Analytics, WalletPage) read `solanaAddress` from `WalletAuthContext`. Capture `publicKey` after connect via a `useRef` flag + `useEffect` to avoid stale closure issues in async handlers.

**Wallet persistence + explicit-disconnect honour (all 3 chains)**: `app/lib/walletDisconnectFlag.ts` exposes `isDisconnected(chain)` / `setDisconnected(chain)` / `clearDisconnected(chain)` over three SSR-safe localStorage keys: `defidesh_evm_disconnected`, `defidesh_solana_disconnected`, `defidesh_sui_disconnected`. `app/providers.tsx` reads each Solana / Sui flag synchronously in a `useState` initializer and passes the inverse as the `autoConnect` prop to `<WalletProvider>` (Solana adapter) and `<SuiWalletProvider>` (dapp-kit), so providers mount with autoConnect already gated — no race with the adapter's silent-reconnect path. EVM (wagmi v3) reconnects from its own internal storage on mount, so a sibling component `<EvmDisconnectGate>` inside `<WagmiProvider>` checks the flag once on mount and force-calls `useDisconnect().disconnect()` if set. All three navbar disconnect buttons (`handleEvmDisconnect`, `handleSolanaDisconnect`, `handleSuiDisconnect`) call `setDisconnected(chain)` BEFORE the underlying adapter disconnect.

**CRITICAL — flag-clear lives in the provider watchers, NOT in click handlers**: clearing the disconnect flag at click time was the source of a silent-reconnect bug — if the connect attempt failed (locked Phantom, dismissed prompt) the flag was already gone, and the adapter's cached session would silently reconnect on the next click without the wallet ever asking for a password. Fix: three sibling `<EvmConnectionWatcher>` / `<SolanaConnectionWatcher>` / `<SuiConnectionWatcher>` components inside their respective providers each call a shared `useClearOnConfirmedConnect(chain, connected)` hook that fires `clearDisconnected(chain)` ONLY when (a) `connected` is `true` AND (b) the value transitioned AFTER mount (the hook skips its first effect run via a `useRef` flag). The "skip first run" guard prevents the brief moment of `connected=true` that wagmi reports from its storage before `<EvmDisconnectGate>` calls `disconnect()` from prematurely clearing the flag during page load. Net behaviour: a successful confirmed connection — and only that — re-enables silent autoConnect on the next refresh; failed attempts leave the flag intact so the wallet extension keeps prompting for unlock.

Result: refresh keeps every connected chain alive without prompting; explicit Disconnect on any chain stays disconnected through refreshes; clicking Connect again triggers the wallet extension's natural unlock prompt every time the previous attempt failed. First-time visitors (no flags) get the default autoConnect path. All `localStorage` reads wrapped in `typeof window !== "undefined"` guards so SSR never touches it.

- **Three places that hold canonical CoinGecko IDs — kept intentionally separate**: (1) `TICKER_TOKENS` in `app/components/PriceTickerStrip.tsx` — per-wrapper prices for the ticker (WBTC→`wrapped-bitcoin`, CBBTC→`coinbase-wrapped-btc`); (2) `SYMBOL_TO_CG_ID` in `app/hooks/useWalletTokens.ts` — wallet-balance aggregation map where WBTC/CBBTC/TBTC/UBTC are DELIBERATELY aliased to `bitcoin` so all BTC variants in a wallet roll up to the same USD price (changing this regresses wallet totals across dashboard / analytics / `/dashboard/wallets`); (3) per-route `KNOWN_TOKENS` maps in each protocol API route under `app/api/*/route.ts`. AERO (`aerodrome-finance`), TAO (`bittensor`), and ZCASH/ZEC (`zcash`) live in `SYMBOL_TO_CG_ID` purely additively. `/api/prices` itself is a generic CoinGecko passthrough (`?ids=...`) so it does NOT hold its own map; the header comment in that file documents the canonical IDs for reference.
